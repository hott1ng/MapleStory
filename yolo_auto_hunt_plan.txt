YOLO 自动刷怪脚本方案记录

说明：

本方案仅用于自有、单机、测试或研究环境中的视觉 AI 实验。
不包含绕过反作弊、隐藏脚本、规避检测、破坏游戏公平性的实现内容。


一、当前项目状态

当前项目已经具备或正在准备以下能力：

1. 通过窗口截图获取游戏画面。
2. 使用 YOLO 模型识别怪物。
3. 当前数据集类别为：

   0: mogu

4. 当前阶段重点是得到怪物检测框和中心点坐标。
5. 后续目标是在识别坐标基础上，增加目标选择、移动决策、路径规划和状态机。


二、推荐总体架构

推荐不要把识别结果直接变成按键操作，而是拆成多个模块：

截图/视频流
  -> YOLO 识别怪物
  -> 检测结果稳定处理
  -> 场景状态建模
  -> 目标选择
  -> 路径规划
  -> 行为状态机
  -> 动作执行
  -> 失败检测与重新规划

每个模块只负责一件事，方便调试和替换。


三、第一阶段：稳定识别

目标：

只做实时检测，不做自动操作。

需要输出：

1. 怪物数量。
2. 每个怪物的 bbox。
3. 每个怪物的中心点 center_x、center_y。
4. 每个检测框的置信度 conf。

建议数据结构：

state = {
    "monsters": [
        {
            "class": "mogu",
            "x1": 100,
            "y1": 200,
            "x2": 160,
            "y2": 260,
            "center_x": 130,
            "center_y": 230,
            "conf": 0.86
        }
    ]
}

建议：

1. 继续补充怪物标注数据。
2. 先做到 50-100 张截图。
3. 截图应覆盖不同地图、不同背景、不同姿态、不同遮挡。
4. 先保持单类别 mogu，不急着增加角色、平台、道具类别。


四、第二阶段：目标选择

目标：

从多个怪物中选出当前最适合处理的目标。

最小可用策略：

1. 过滤低置信度目标。
2. 选择离画面中心或角色预估位置最近的怪物。
3. 优先选择同一水平线附近的怪物。

如果暂时没有识别角色，可以先用画面中心附近作为角色近似位置：

player_estimate_x = window_width / 2
player_estimate_y = window_height * 0.65

目标评分示例：

score = 水平距离成本 + 垂直距离成本 - 置信度奖励

优先选择 score 最低的怪物。

简单规则：

1. 怪物和角色预估 y 坐标接近，优先级高。
2. 怪物距离角色预估 x 坐标近，优先级高。
3. 置信度太低的目标忽略。
4. 目标连续多帧出现，优先级高。


五、第三阶段：检测结果稳定处理

YOLO 检测会抖动，不能每一帧都完全相信。

建议增加短期记忆：

1. 保存最近 5-10 帧检测结果。
2. 对中心点做滑动平均。
3. 同一个怪物连续多帧出现后再作为有效目标。
4. 某个目标消失 2-3 帧，不要立刻认为怪物死亡。

目标状态可以分为：

1. candidate：刚出现，还不稳定。
2. active：连续出现，可以作为目标。
3. lost：短暂丢失，等待恢复。
4. removed：长时间消失，移除目标。


六、第四阶段：同平台移动逻辑

推荐先只做同平台逻辑，不要一开始就做全地图巡航。

同平台判断的简化规则：

如果怪物 center_y 和角色预估 y 差距小于阈值，则认为在同一层。

示例：

abs(monster.center_y - player_estimate_y) < 80

同平台移动规则：

1. 怪物在右边，向右移动。
2. 怪物在左边，向左移动。
3. 进入攻击范围，停止移动并攻击。
4. 怪物消失或距离过远，重新选择目标。

攻击范围示例：

attack_range_x = 120
attack_range_y = 80

如果：

abs(monster.center_x - player_x) < attack_range_x
并且
abs(monster.center_y - player_y) < attack_range_y

则进入攻击状态。


七、第五阶段：行为状态机

不要用大量零散 if 直接控制动作，建议使用状态机。

推荐状态：

1. IDLE
   空闲，等待画面稳定。

2. FIND_TARGET
   从当前检测结果中选择目标。

3. MOVE_TO_TARGET
   向目标靠近。

4. ATTACK
   进入攻击范围后执行攻击动作。

5. LOOT
   如果后续识别掉落物，则进入拾取逻辑。

6. RECOVER
   处理卡住、识别丢失、异常状态。

7. REPLAN
   当前目标不可达或消失时重新规划。

状态流转：

IDLE
  -> FIND_TARGET
  -> MOVE_TO_TARGET
  -> ATTACK
  -> LOOT
  -> FIND_TARGET

异常时：

任意状态
  -> RECOVER
  -> REPLAN
  -> FIND_TARGET


八、第六阶段：路径规划方案

横板游戏不适合直接用普通网格 A*。

推荐使用：

平台图 + 动作边 + A*

地图抽象：

1. platform：可站立平台。
2. rope：绳子或梯子。
3. portal：传送点。
4. drop_point：可下落位置。
5. jump_point：可跳跃位置。
6. danger：危险区域。

图结构：

节点：

平台上的关键点，例如平台左端、右端、绳子脚下、跳点、落点。

边：

角色可以完成的动作，例如：

1. walk_left
2. walk_right
3. jump_left
4. jump_right
5. drop_down
6. climb_up
7. climb_down
8. use_portal

路径搜索结果不应该是一串像素点，而应该是一串动作：

walk_right to x=320
jump_right
climb_up
walk_left to x=260
attack

建议开发顺序：

1. 先做同平台移动。
2. 再手工配置固定巡逻路线。
3. 再识别或配置平台点位。
4. 最后再做完整平台图 A*。


九、第七阶段：巡逻路线

在没有完整平台识别前，可以先用固定巡逻点方案。

巡逻点示例：

route = [
    {"x": 250, "y": 420, "action": "walk"},
    {"x": 600, "y": 420, "action": "walk"},
    {"x": 680, "y": 420, "action": "jump"},
    {"x": 400, "y": 300, "action": "walk"}
]

逻辑：

1. 当前画面有怪，优先处理怪物。
2. 当前画面没有怪，沿巡逻路线移动。
3. 移动过程中如果发现怪物，打断巡逻，进入 FIND_TARGET。

这个方案比一开始做全自动寻路更容易落地。


十、第八阶段：失败检测

自动逻辑必须有失败检测，否则很容易卡住。

建议检测：

1. 连续多帧识别不到怪物。
2. 连续多帧无法判断角色位置。
3. 目标长时间没有接近。
4. 当前动作执行超过最大时间。
5. 角色位置长时间没有变化。
6. 画面变化异常。

处理方式：

1. 停止当前动作。
2. 回到 IDLE 或 REPLAN。
3. 重新选择目标。
4. 必要时暂停脚本等待人工处理。

硬停止条件：

如果无法确认当前画面状态，不继续执行动作。


十一、推荐落地顺序

第一步：

保持现有 YOLO 实时识别逻辑，继续提高 mogu 检测准确率。

第二步：

加入检测结果稳定处理，避免坐标抖动。

第三步：

实现目标选择，只打印当前目标，不执行动作。

第四步：

实现同平台靠近逻辑，只输出动作意图，例如：

move_left
move_right
attack
wait

第五步：

将动作意图接入状态机。

第六步：

加入固定巡逻点，不做复杂寻路。

第七步：

加入卡住检测和重新规划。

第八步：

再考虑平台图、绳子、跳跃、传送点等高级路径规划。


十二、最小可行版本

最小可行目标：

1. 实时识别 mogu。
2. 过滤 conf 太低的目标。
3. 选择最近的同层怪物。
4. 输出动作意图：

   move_left
   move_right
   attack
   wait

5. 目标消失后重新选择。

最小状态机：

IDLE
FIND_TARGET
MOVE_TO_TARGET
ATTACK
REPLAN

最小决策规则：

1. 没有怪物：wait 或巡逻。
2. 有怪物但不在攻击范围：向怪物方向移动。
3. 有怪物且在攻击范围：attack。
4. 目标丢失：REPLAN。


十三、角色外观和时装变化处理方案

问题：

不同角色的发型、时装、武器、特效差异很大，如果直接用 YOLO 识别“完整角色外观”，模型很容易记住某一套衣服，而不是学会稳定定位角色。

推荐原则：

不要把角色外观当作唯一定位依据。

更稳的方案是：

画面中心估算
  + 稳定 UI 或头顶标记推断
  + player 类别检测校准
  + 多帧稳定追踪


1. 第一优先：使用画面中心估算角色位置

横板游戏镜头通常会跟随角色移动，角色多数时候接近画面中心偏下位置。

前期可以先使用估算位置：

player_x = window_width / 2
player_y = window_height * 0.60 到 0.70

优点：

1. 不受时装、发型、武器影响。
2. 不需要额外标注角色数据。
3. 适合当前只识别 mogu 的阶段。
4. 足够支持同平台找怪、判断左右方向和攻击距离。

适用逻辑：

1. 判断怪物在角色左边还是右边。
2. 判断怪物是否在同一层。
3. 判断是否进入攻击范围。
4. 控制简单巡逻路线。


2. 第二优先：识别稳定锚点

如果游戏画面中存在比较稳定的角色相关标记，可以优先识别这些锚点，而不是识别角色身体。

可选锚点：

1. 角色名。
2. 角色头顶血条。
3. 角色头顶固定标记。
4. 小地图角色点。
5. 固定 UI 状态区域。

推断方式：

检测到角色名或头顶标记后，可以根据固定偏移推算角色身体中心。

示例：

player_x = name_center_x
player_y = name_center_y + fixed_offset_y

这种方式通常比直接识别不同服装的角色更稳定。


3. 第三优先：增加 player 类别

如果后续确实需要 YOLO 识别角色，不要按时装、发型、武器拆分类别。

不推荐：

player_red_cloth
player_blue_cloth
player_hat
player_no_hat

推荐统一标注为：

names:
  0: mogu
  1: player

训练数据应覆盖：

1. 不同发型。
2. 不同时装。
3. 不同武器。
4. 不同朝向。
5. 站立、跳跃、攻击、爬绳等动作。
6. 被怪物、特效、地形遮挡。
7. 不同地图背景。
8. 不同亮度和技能特效。

数据量建议：

player: 300-800 张
mogu: 300-800 张

如果 player 数据太少，模型会过拟合到某一套外观。


4. 推荐融合策略

角色位置不要只相信单一来源。

推荐优先级：

1. 如果 player 检测置信度高，使用 YOLO 的 player 坐标。
2. 如果 player 检测不稳定，但角色名或头顶标记稳定，使用锚点推断坐标。
3. 如果都没有，则回退到画面中心偏下估算坐标。

伪逻辑：

if player_detect_conf >= 0.6:
    player_pos = yolo_player_center
elif name_or_marker_found:
    player_pos = marker_center + fixed_offset
else:
    player_pos = screen_center_estimate

安全规则：

1. 如果连续多帧无法确认角色位置，不继续执行动作。
2. 如果 player 位置突然大幅跳变，先进入 RECOVER。
3. 如果估算位置和检测位置差距过大，短暂停止并重新定位。
4. 角色定位不稳定时，只允许 wait，不允许复杂跳跃或跨平台动作。


5. 当前阶段建议

当前项目最适合：

1. 暂时不急着识别角色外观。
2. 继续让 YOLO 专注识别 mogu。
3. 使用画面中心偏下位置作为 player 估算坐标。
4. 用这个估算坐标完成目标选择、同平台移动和攻击范围判断。
5. 等状态机稳定后，再补充 player 数据集。

这样可以最大程度避免时装变化带来的识别不稳定。


十四、检测范围 ROI 优化方案

目标：

后续可以只检测画面中的指定区域，减少无关区域干扰，并提高推理速度。

例如：

只检测图片右下角 1/4。


1. 基本思路

不要让 YOLO 直接检测整张截图，而是在推理前先裁剪截图。

流程：

窗口截图
  -> 根据 ROI 裁剪图片
  -> YOLO 检测裁剪图
  -> 将检测框坐标加回 ROI 偏移
  -> 输出原窗口坐标系下的 Detection


2. 右下角 1/4 示例

假设原图宽高为：

width = image.width
height = image.height

右下角 1/4 的范围是：

left = width * 0.5
top = height * 0.5
right = width
bottom = height

PIL 裁剪示例：

crop_box = (
    int(image.width * 0.5),
    int(image.height * 0.5),
    image.width,
    image.height,
)

cropped_image = image.crop(crop_box)


3. 坐标还原

YOLO 对 cropped_image 的检测结果是裁剪图内部坐标。

如果后续逻辑需要窗口内坐标，必须加回偏移：

offset_x = crop_box[0]
offset_y = crop_box[1]

x1 = x1 + offset_x
x2 = x2 + offset_x
y1 = y1 + offset_y
y2 = y2 + offset_y

规则：

裁剪图坐标 + 裁剪区域左上角偏移 = 原窗口坐标


4. 推荐参数设计

后续可以在 realtime_detect.py 中增加参数：

--roi 0.5,0.5,1.0,1.0

含义：

left_ratio = 0.5
top_ratio = 0.5
right_ratio = 1.0
bottom_ratio = 1.0

表示只检测右下角 1/4。

也可以预设常用区域：

--roi-preset right-bottom
--roi-preset left-bottom
--roi-preset center
--roi-preset full


5. Detection 输出要求

即使 YOLO 检测的是裁剪图，最终输出的 Detection 仍然应该保持窗口坐标。

也就是说：

Detection.bbox
Detection.center
Detection.distance_from_center

都应该基于完整窗口坐标计算。

这样后续状态机、路径规划、攻击范围判断不需要关心是否启用了 ROI。


6. 使用场景

适合用于：

1. 只关心角色右侧刷怪区域。
2. 只检测固定平台区域。
3. 排除 UI 区域，避免误识别。
4. 降低 CPU 推理压力。
5. 做分区域巡逻，例如先检测右侧，再检测左侧。


7. 当前结论

ROI 检测是后续优化点，不影响当前最小可行版本。

当前仍建议先保持全图检测，等 Detection 数据结构、目标选择和状态机稳定后，再加入 --roi 参数。


十五、后续可扩展方向

1. 增加 player 类别，真实识别角色位置。
2. 增加 item 类别，支持掉落物识别。
3. 增加 platform 类别，辅助路径规划。
4. 增加 rope 或 ladder 类别，支持上下层移动。
5. 增加目标追踪 ID，减少目标切换。
6. 增加可视化调试面板，显示当前状态、目标、动作意图。
7. 增加日志记录，方便回放和排查问题。


十六、当前建议结论

当前最适合的方案是：

先做“YOLO 识别 + 目标选择 + 同平台状态机”，不要立刻做完整自动寻路。

原因：

1. 当前数据集还比较小，识别稳定性优先级最高。
2. 只识别怪物时，暂时无法可靠判断角色和平台。
3. 同平台逻辑最容易验证闭环。
4. 固定巡逻点比完整地图路径规划更容易落地。
5. 等识别、状态机、失败检测稳定后，再扩展到平台图和 A*。
